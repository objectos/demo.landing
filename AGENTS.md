# AGENTS.md

Objectos Way landing-page demo: a Java modular web app (`module demo.landing`) built with `objectos.way` and H2. It runs standalone in development and is embedded by the Objectos website.

## Commands

The `Makefile` is the real build definition; the README's "Running Locally" section is unfinished.

- Run every command from the repository root. Runtime code resolves `work/`, `web-resources/`, `resources/`, and `test/testng.xml` relative to the current directory.
- `JAVA_HOME` must point to a JDK that supports `--release 25`; the Makefile aborts without it.
- `make` / `make test` — compile, compile tests, boot `demo.landing.StartTest`, and run the TestNG suite.
- `make compile` — main sources only.
- `make re-test` — clear the test runtime marker and rerun.
- `make dev` — run `StartDev` on `http://localhost:8006`.
- `ENABLE_DEBUG=1 make dev` — same, with JDWP listening on `localhost:7000`.
- `make db-run` — open the H2 shell for the development database.
- `make db-clean` — delete the development database; `make clean` deletes all of `work/`.
- `make jar` / `make install` — build or install `br.com.objectos:demo.landing:004-SNAPSHOT`.
- `make source-gen` — regenerate `Source.java`; `make source-gen@test` prints the escaping test fixture `SourceGen.test`.
- `make eclipse` — regenerate `.classpath` and `.project` (do not hand-edit them).

There is no Maven, Gradle, CI, linter, or formatter configuration.

## Dependencies

- Dependency resolution is done by `Resolver.java` from the Makefile into `~/.cache/objectos/{repository,resolution}`; there is no lockfile.
- If that cache is read-only, the H2 module rebuild fails. Pass writable locations to `make`, for example `LOCAL_REPO=/writable/repo RESOLUTION_DIR=/writable/resolution`, with the cached artifacts copied or symlinked there.
- `objectos.way` is the mutable `br.com.objectos/objectos.way/0.4.0-SNAPSHOT` resolved from the local cache. If compile errors say `objectos.way` APIs are missing (for example `TestableNodes.item`, `row`, or `c(Component)`), the cached snapshot is out of sync with this checkout; align the dependency before changing demo code.

## Architecture

- `main/demo/landing/` — embedding boundary and bootstrapping. `Start` wires the injector, H2 database, migrations, and HTTP server. `StartDev` adds the reloading handler and `BootModule`/`DevModule`. `StartTest` boots the app with an in-memory H2 database and does not bind an HTTP port.
- `main/demo/landing/app/` — the demo itself: route handlers (`Home`, `Movie`, `Seats`, `Confirm`, `Ticket`, `Poster`, `NotFound`), `*Model` query/state classes, `*View` renderers, `AppCtx`, and `UiShell`.
- `main/demo/landing/dev/` — the landing-page wrapper around the embedded demo.
- `LandingDemo` is the public embedding API; `AppCtx` implements it. `module-info.java` exports only `demo.landing`.
- Public demo routes are under `/demo.landing/...`; `/ui/styles.css` and `/ui/script.js` are generated, `web-resources/` is served as static files, and posters come from `resources/demo/landing/`.
- Development data lives in `work/demo.landing.mv.db`; schema and seed migrations are in `LandingDemoDb`. Tests use an in-memory database and apply schema migration only.

## Generated code

- `main/demo/landing/app/Source.java` is generated by `SourceGen.java` from every `*.java` in that directory. Never edit it by hand. Compile regenerates it when an app source is newer.
- A new class in that package becomes `Source.<ClassName>` automatically (`SourceModel.java` becomes `SourceModel_`), but it only appears in the rendered source panel if added to the relevant `opts.sources` list; `UiShell` always includes `AppCtx`, `AppView`, `UiIcon`, and `UiShell`.
- The source panel embeds full file contents, so stale `Source.java` makes the UI display old code even when the compiled app is current.

## Tests

- Tests use TestNG, not JUnit.
- Test classes must be annotated `@Listeners(Testing.class)`. That listener boots the app once via `StartTest.boot()` and exposes the shared `Testing.INJECTOR` and `Testing.HANDLER`.
- `test/testng.xml` includes the packages `demo.landing.app` and `demo.landing.app2`. All tests share one app boot and one in-memory H2 database, so the suite is stateful; run it as a whole.
- Reports are written to `work/test-output`. The root `test-output/` directory is stale output from older runs.
- There is no single-test flag: `StartTest.run()` hardcodes `test/testng.xml`, and the Makefile's `TEST_ARGS` is ignored by `StartTest`. To run one class, temporarily narrow `test/testng.xml` (replace `<packages>` with `<classes><class name="..."/></classes>`), then rerun.
- Most tests load SQL fixtures through `Testing.rollback` and `Testing.load`; tests in `test/demo/landing/app2/` use `Testing.commit` and priorities for concurrent-reservation cases.
- Tests exercise package-private classes through the `--add-exports`/`--add-reads` flags in the Makefile. Add new test packages to `TEST_ADD_EXPORTS` and `TEST_ADD_READS` when needed.

## Conventions

- Java sources use 2-space indentation, `final` locals and fields where possible, and a `final` modifier on many methods.
- New Java files must carry the Apache-2.0 header used throughout the repository.
- Add new external modules to both `main/module-info.java` and the Makefile dependency variables; module-path builds are the default.

## TDD

This project is developed using TDD:

- Write tests first.
- Write tests first.
- Never write production code when there's no test code.
- The tests should drive the design of the class being developed.
- Don't limit yourself to the happy path; think hard on what ways can a functionality fail.
- Don't limit yourself to unit tests; include integration tests if you feel the need for them.
- Before modifying an existing production class, ensure that test coverage for the class is adequate.

## Code style

### Class declarations

When adding methods to a class, keep them sorted. First, by access level:

- public
- default (package-private) access
- protected
- private

Then sorted alphabetically.

### Method invocations

Avoid having more than one method invocation in the same statement or sub-statement.

The following should be avoided:

```java
return append(s.subSequence(start, end));
```

The innermost method invocation should be declared as a local variable instead:

```java
final CharSequence sub;
sub = s.subSequence(start, end);

return append(sub);
```

Also, the use of method chaining should be minimized.
